# 架构决策记录（ADR）

本目录记录 ReelAgent 的架构决策。每篇 ADR 描述一个**难以回滚**的技术选择，
以及当时为什么这么选、付出了什么代价、否决了哪些方案。

## 为什么要有 ADR

代码能告诉我们「是什么」，但说不出「为什么不是别的样子」。
当半年后有人问「为什么不用 Celery」，答案不应该是
「不知道，一直就是这样」。ADR 的价值在于：

1. **保留否决理由**。被拒绝的方案往往看起来更好——
   记下它们为什么不适合**当时**的约束，避免反复重新讨论。
2. **让代价显式**。每个决策都有负面后果。
   写下来才能在后果真的出现时快速判断「这是预期内的代价」
   还是「我们的假设错了」。
3. **新人上手**。读一遍 ADR 就能理解系统的形状，
   而不需要读完全部代码再反推。

## 格式

每篇 ADR 使用以下结构：

```markdown
# ADR NNNN：<决策标题>

- **状态**：提议 | 已接受 | 已废弃 | 被 <ADR NNNN> 取代
- **日期**：<日期或版本>
- **决策者**：<角色>
- **相关文件**：<代码路径>

## 背景
当时面临什么问题、有哪些约束。

## 决策
具体决定了什么。要足够精确，让读者能据此判断代码是否符合决策。

## 后果
### 正面
### 负面 / 代价
### 需要长期注意

## 备选方案
每个被否决的方案：优点 → 否决理由。不用「不好」这种评价，
要说清在**当时的约束下**为什么不可行。

## 参考
```

## 约定

- **文件命名**：`NNNN-kebab-case-title.md`，编号四位零填充且不复用。
- **只追加**：ADR 一经「已接受」就**不修改正文**。
  需要改变决策时写一篇新 ADR，并把这老的一篇状态改为
  `被 ADR NNNN 取代`（同时在新 ADR 里引用旧的）。
  这保留了决策的历史轨迹——「我们曾经这么想，后来因为 X 改了」。
- **例外**：修正错别字、补充失效的链接、追加「参考」条目是允许的。
  但任何改变**语义**的编辑都不允许。
- **什么时候写**：见 [CONTRIBUTING.md](../../CONTRIBUTING.md) 的
  「什么时候必须写 ADR」一节。

  因此这个决策实际上还没做。

  生产环境的 schema 演进方式尚未定型。
- **`Storage` 抽象的租户校验下沉**
  （见 [ADR 0007](0007-tenant-scoped-artifact-storage-keys.md) 的方案 E）。
- **额度账本的归档 / 分区策略**。
- **`reelagent_credits_consumed_total` 的 `org_id` 标签造成的基数膨胀**。
- **多版本评测对比报告的形态**。
